## 설계 요약
'용량 줄이기'(이미지)·'PDF 용량 줄이기'를 목표 용량 작업 5개(500KB·1MB·2MB·5MB·10MB)로 바꾼다. 원형 변환에서는 '용량 줄이기' 칸 하나로 보이고, 끈 채 0.5초 머무르면 그 칸 바깥으로 5칸이 펼쳐진다. 변환은 결과 크기를 직접 재면서 품질·해상도를 단계적으로 낮춰 목표 아래에 맞춘다.

## 구성
- `ConvertOp`(Converter.swift): `.shrink`, `.pdfShrink`를 없애고 `shrink500K, shrink1M, shrink2M, shrink5M, shrink10M` 추가. 이미지·PDF 공용(파일 종류로 갈라 처리).
  - `targetBytes`: 500_000 / 1_000_000 / 2_000_000 / 5_000_000 / 10_000_000(10진, intent 제약 "둘 중 작은 값" = 10진).
  - `title` "1MB 이하", `short` "1MB". 이미지·PDF의 칸 목록에서 예전 자리에 5개가 들어간다.
- `Converter.convert(_:_:note:)`: 마지막에 `note: (String) -> Void = { _ in }` 인자 추가(다른 작업은 안 씀). `run`은 파일별 알림을 모아 `done(outputs, errors, notes)`로 돌려준다. `--convert` CLI는 알림을 그대로 출력.
- 이미지 `shrinkImage(src, target)`:
  1. 원본 크기 ≤ 목표 → 파일을 만들지 않고 알림 "이미 1MB 이하예요".
  2. 방향 적용해 읽고 흰 배경에 얹는다(투명 → 흰색).
  3. 긴 변을 원본 → ×0.8씩 줄이며(최소 800px, 원본이 더 작으면 원본만) 각 크기에서 JPEG 품질을 0.3~0.9 사이 이분 탐색(5번)해 목표 아래 중 가장 높은 품질을 고른다. 메모리에서 인코딩해 크기를 잰다.
  4. 어느 단계도 못 맞추면 가장 작은 결과를 저장하고 알림 "목표에 못 맞췄어요 (1.3 MB)".
- PDF `shrinkPDF(src, target)`:
  1. 원본 크기 ≤ 목표 → 알림만.
  2. 안의 이미지 재압축: `QuartzFilter`(JPEG 품질·해상도 지정, Preview '파일 크기 줄이기'와 같은 방식)로 다음 순서로 써 보고 처음 맞는 것을 쓴다: (0.75, 150dpi) → (0.5, 150) → (0.5, 100) → (0.3, 72). 글자·벡터는 그대로.
     - 2026-11-06 확인: 잡음 이미지 3쪽 11.8MB → 2.17MB / 0.56MB(0.5·100) / 0.24MB(0.3·72), 쪽 수 같음.
  3. 그래도 크면 쪽마다 그림으로 바꿔 같은 쪽 크기의 PDF로 다시 만든다: (150dpi, 0.6) → (110, 0.5) → (80, 0.4) → (60, 0.3). 알림 "글자를 선택·검색할 수 없게 됐어요"를 붙인다.
  4. 다 못 맞추면 가장 작은 결과 저장 + "목표에 못 맞췄어요 (…)".
  - 결과 파일 이름은 기존 `finalize`(라벨 "1MB 이하").
- `WheelItem`(ConvertWheel.swift): `children: [WheelItem] = []` 추가.
- `WheelMath.children(of: Wedge, count:, arc:)`(순수, 자체 검사 대상): 부모 칸 바깥(r0 = 부모 r1 + 6, 두께 58)에 칸당 16°로, 부모 가운데 각을 중심으로 펼친다. 반원(화면 끝)일 때는 반원 범위 안으로 밀어 넣는다.
- `ConvertWheelView`: 자식이 있는 칸에 0.5초 머무르면 펼침(`expanded`). 펼친 동안 칸 찾기는 자식 칸을 먼저 본다. 자식·부모가 아닌 다른 칸으로 가면 접는다. 부모 칸 자체에 놓으면 변환하지 않고 원을 닫은 뒤 펫이 "칸에 잠깐 올려 두면 목표 용량이 펼쳐져요"라고 말한다. 패널 크기는 자식 칸까지 들어가게 키운다.
- `PetController.convertItems`: `targetBytes`가 있는 작업을 모아 부모 칸 '용량 줄이기'(동작 고리) 하나로 묶는다. `convert` 완료 메시지는 알림이 있으면 알림을 보여 준다(여러 개면 "첫 알림 외 N건", 4초).

## 데이터 흐름
파일을 끌어 곰에 옴 → 원형 칸 → '용량 줄이기'에 0.5초 → 5칸 펼침 → '1MB'에 놓음 → `Converter.run(.shrink1M, urls)` → 파일마다 따로(intent 추정 그대로) `shrinkImage`/`shrinkPDF` → 임시 파일에서 크기 확인 → `finalize`로 원본 옆에 저장 → 펫 말풍선(완료/알림/오류).

## 오류 처리
- 열 수 없는 이미지·PDF: 지금처럼 오류("이미지를 열 수 없어요"/"PDF를 열 수 없어요").
- QuartzFilter 쓰기 실패(`write`가 false): 그 단계는 건너뛰고 다음 단계로. 모든 단계가 실패하면 "PDF를 저장하지 못했어요".
- 섞인 파일(이미지+PDF)을 놓으면 지금처럼 공통 칸이 없어 용량 칸이 안 나온다.
- 이미 작은 파일: 오류가 아니라 알림. 결과 0개라도 "실패"로 세지 않는다.

## 확인 방법
- `swift build` 종료 코드 0.
- `--selftest`에 추가:
  - `WheelMath.children`: 5칸, 모두 부모 바깥, 반원일 때 범위 안.
  - 칸 목록: 이미지·PDF에 5개 목표 작업, `.shrink` 없음.
  - 잡음 이미지(약 3000×2000)를 임시 폴더에 만들어 `shrink500K` → 결과 ≤ 500,000바이트, 작은 이미지 → 결과 없음 + "이미" 알림.
  - 잡음 이미지 3쪽 PDF → `shrink500K` → ≤ 500,000바이트, 쪽 수 같음.
- `--convert shrink1M <실제 사진>`으로 성공 기준 1 확인(8MB 사진은 사용자 파일이 필요 — 없으면 만든 잡음 이미지로 대신하고 보고).
- 원형 칸 펼침은 화면을 볼 수 없어 사용자 확인 필요(확인 못 함으로 보고).

## 고려한 대안
- 처음부터 5칸: 이미지 칸이 15개로 좁아짐(인터뷰에서 펼침 선택).
- PDF `optimizeImagesForScreenOption`(지금 방식): 품질을 고를 수 없어 목표에 맞출 수 없다.
- 작업 하나 + 목표를 따로 넘기기(`ConvertOp` 바깥 인자): `run`·CLI·사용 횟수 기록까지 인자를 끌고 다녀야 한다. 목표별 작업 5개가 기존 구조(작업 = 이름 하나)에 맞는다.

## 우려
- 이미지는 결과가 JPEG라 PNG 스크린숏도 JPEG가 된다(intent 제약 그대로).
- 큰 사진에서 인코딩을 여러 번(최대 크기 단계 × 5번) 해 몇 초 걸릴 수 있다. 변환 중 진행 링은 지금처럼 돈다.
- 쪽을 그림으로 바꾸는 단계는 글자가 흐려질 수 있다. 목표가 작을수록 심하다.
- 반원(화면 끝)에서 펼친 칸이 화면 밖으로 조금 나갈 수 있다(범위 안으로 밀어 넣지만 반지름이 커진다).
- 사용 횟수 기록(`convertUse`)의 예전 `shrink`·`pdfShrink` 값은 남지만 쓰이지 않는다(지우지 않음).
